# 2026-09-29 — полное чтение проекта с журналом не обрывается вместе с запросом (beads-web-hoj)

Большой проект с журналом (1150 задач, 2841 комментарий) не открывался:
«Error loading beads: signal timed out». Страница ждала любой ответ API 10 с,
а первое полное чтение такого проекта идёт 11–19 с. Хуже того, когда страница
обрывала запрос, axum выбрасывал обработчик вместе с полным чтением, копия не
сохранялась, и следующий запрос начинал сначала. Так как страховочное
перечитывание раз в 10 минут тоже идёт внутри опроса, доска могла застыть
навсегда. Исправлено в двух местах: `store_detached` в
`server/src/routes/journal.rs` запускает полное чтение отдельной задачей
(`tokio::spawn`), которая сама держит блокировку проекта (`lock_owned`) и сама
кладёт копию в слот; запрос только ждёт ответа по каналу. А `beads.read` в
`src/lib/api.ts` ждёт 60 с вместо общих 10 с; остальные вызовы — по-прежнему 10 с.
Ручная проверка на релизной сборке: запрос, оборванный через 3 с, — полное
чтение всё равно закончилось через 18,7 с, следующие запросы — 1,2–1,4 с без
нового полного чтения.

**Почему так.** Отдельная задача с блокировкой внутри сохраняет правило «не
больше одного вызова bd на проект одновременно»: пока она работает, остальные
запросы ждут и потом берут готовую копию. Результат возвращается через канал
(`oneshot`), а не через `JoinHandle`, чтобы задача знала, что её запрос ушёл, и
сама написала об этом в журнал — иначе ошибку полного чтения никто бы не
увидел. Паника в задаче закрывает канал — запрос получает ошибку и уходит на
прежний путь через bd CLI, старая копия остаётся. Дочитывание хвоста журнала
осталось внутри запроса: копия меняется только после того, как весь хвост
прочитан (`apply_all` без ожиданий внутри), так что обрыв на середине её не портит.

**Что проверить, если сломается.** В журнале сервера после оборванного запроса
должна быть пара `journal baseline finished` и `journal baseline finished after
its request was gone, copy kept`; ошибка без запроса — `journal baseline failed
after its request was gone`. Если на доске снова «signal timed out» — смотреть
`duration_ms` у `journal baseline finished`: больше 60 с значит, что проект
перерос ограничение в `BEADS_READ_TIMEOUT_MS`.

**Что оставлено как есть.** Общие 10 с для остальных вызовов API. Дочитывание
хвоста не вынесено в отдельную задачу — оно короткое и безопасно к обрыву.
