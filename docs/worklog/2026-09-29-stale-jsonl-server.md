# 2026-09-29 — сервер: пометка старой выгрузки issues.jsonl (beads-web-cgl.1)

Когда bd установлен, но отказывается читать базу (например, «schema version
mismatch» после обновления bd), `read_beads` (`server/src/routes/beads.rs`)
молча отдавал `.beads/issues.jsonl` — выгрузку, которая могла отстать на
месяцы. Теперь в этом случае в ответ `/api/beads` добавляются два поля:
`stale_reason` — текст отказа bd (без пробелов по краям, не длиннее 300 знаков
вместе с «…» на конце, режется по буквам, а не по байтам) и
`jsonl_modified_at` — время изменения файла в RFC 3339, UTC, с точностью до
секунды (`2026-07-14T10:22:03Z`). Остальные поля (`beads`, `source: "jsonl"`,
`comment_total`) прежние. Страница (beads-web-cgl.2) по этим полям покажет
плашку и отключит изменения.

**Почему так.** Поля собирает чистая функция `stale_jsonl_fields` (плюс
`trim_stale_reason` для обрезки) — на неё и написаны тесты; обёртка
`stale_fields_for_jsonl` читает время файла, спрашивает `find_bd()` и пишет
одну строку в журнал сервера. Если bd не найден, полей нет: такие проекты
законно живут на одном `issues.jsonl`, и данные в нём самые свежие. Если время
файла не прочиталось — пропадает только `jsonl_modified_at`. Причина всегда
берётся из ступени 2b (`bd list`), даже если перед ней упал журнал событий
(ступень 2a) — именно она решает, уйдём ли мы на выгрузку.

**Что проверить, если сломается.** В журнале сервера подряд две строки warn:
`bd CLI failed for <путь>: <ошибка>` и `bd failed, serving stale issues.jsonl
— the board shows an old copy` с полями `project` и `jsonl_modified_at`.
Вторая есть — поля должны быть в ответе. Проверка вручную: папка с
`.beads/issues.jsonl` и без базы (`bd list` там падает с «no beads database
found»), запрос `/api/beads?path=<папка>`. Папка с `.beads/`, но без
`issues.jsonl` — прежний 404.

**Что оставлено как есть.** Страница (beads-web-cgl.2), счётчики на главной
(кэш пишется с `source = "jsonl"`, как и раньше), `journal.rs`, ответы всех
остальных ступеней.
