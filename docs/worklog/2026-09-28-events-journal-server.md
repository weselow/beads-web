# 2026-09-28 — сервер: копия задач в памяти и журнал bd events (beads-web-7ux.4.1)

Для файловых проектов во встроенном режиме Dolt `/api/beads` на каждый запрос
запускал полный `bd export` (в `bd sql` встроенный режим не умеет). Если в
проекте включён журнал (`events-journal: true` в `.beads/config.yaml` или
переменная `BD_EVENTS_JOURNAL`), сервер теперь один раз читает всё, держит
копию в памяти и дальше спрашивает только `bd events tail --since N`. Код —
`server/src/routes/journal.rs`, подключение — ступень 2 в `read_beads`
(`server/src/routes/beads.rs`). Ответ: `source: "cli-journal"`, `complete: true`.
На пробном проекте (1002 задачи, 10 тыс. записей журнала, отладочная сборка)
запрос стал занимать ~1–1,4 с вместо 6,4–8 с; первое полное чтение — 6–10 с.

**Почему так.** В записи журнала нет комментариев и связей, поэтому они
берутся из копии, а связи и родитель правятся записями `dep_add`/`dep_remove`.
Последний номер журнала дёшево не узнать, поэтому при полном перечитывании он
ищется чтением журнала потоком (без хранения в памяти); если прошлый номер
известен — только хвост после него. Каждое дочитывание начинается с записи,
виденной в прошлый раз (`--since N-1`): если её нет — журнал подменили, и всё
перечитывается заново. Раз в 10 минут и по `full=1` — полное перечитывание,
потому что `bd dolt pull` в журнал не попадает. Журнал выключили — копия
выбрасывается, чтобы после повторного включения не продолжить со старой.

**Что проверить, если сломается.** В журнале сервера строки
`journal baseline started/finished` (с `duration_ms`), `journal catch-up
applied`, `events journal read failed, falling back to bd CLI`. При любой
ошибке сервер уходит на прежний путь (`source: "cli"`), так что симптом
поломки — снова медленные ответы, а не пустая доска. Ошибка «обрезанного
журнала» (`events_journal_truncated`) приходит в stdout с кодом выхода 1 — если
bd изменит это, чтение будет падать на прежний путь. Проверка на свежем
проекте: `git init` + `bd init --prefix t -q` + `bd config set events-journal true`
во временной папке, затем сравнить обычный ответ с ответом `full=1`.

**Что намеренно не трогали.** `bd serve`, `watch.rs` и поток уведомлений,
ступень 0 и пути `dolt://`, страницу (отдельная задача beads-web-7ux.4.2) и
переключатель журнала в настройках.

## Страница (beads-web-7ux.4.2) и замеры (beads-web-7ux.4.3)

Сервер отвечает `complete: true`, когда в ответе весь список задач, даже если
страница спросила только изменения (`updated_after`). Такой ответ страница не
сливает с прежним списком, а заменяет его целиком — иначе удалённые задачи
оставались бы на доске. После такого ответа второе чтение не делается: раньше
при смене общего числа комментариев страница перечитывала всё ещё раз, а здесь
все комментарии уже в ответе. Для источника `cli-journal` опрос идёт раз в 5 с,
для остальных — по-прежнему раз в 15 с. Код — `src/hooks/use-beads.ts`
(`completeRef`, `JOURNAL_POLL_MS`), тесты — `src/hooks/__tests__/use-beads.test.tsx`.

**Почему страница никогда не шлёт `full=1`.** Флаг `full` у страницы значит
только «не передавать `updated_after`», а не «попросить сервер перечитать
проект». Единственный, кто зовёт `refresh({ full: true })`, — `onCommentAdded`
в `src/app/project/kanban-board.tsx`, то есть каждый добавленный комментарий.
Перечитывание на сервере стоит около 11 с на большом проекте, и доска после
каждого комментария замирала бы на это время. Для журнала оно и не нужно:
ответ без `updated_after` — уже полный список из памяти после дочитывания
журнала, в котором новый комментарий есть.

**Замеры** (выпускная сборка, настоящий встроенный проект: 1148 задач, 2813
комментариев, журнал включён). Первое полное чтение — 23,8 с при холодном
запуске, повторное по `full=1` — 11,1 с; обычные чтения — 1,0–2,4 с против
около 10 с по прежнему пути (`bd list` 6,4 с + `bd sql` 1,3 с + `bd export`
2,5 с на каждый опрос). Список из памяти совпал с полным перечитыванием: 1148
задач, те же статусы, заголовки, родители, число комментариев и связи. Три
одновременных запроса выполнились по очереди, bd параллельно не запускался.
На пробном проекте создание, комментарий, смена статуса и удаление видны при
следующем чтении. Страницу в браузере не проверяли — её поведение покрыто
тестами. Первое открытие проекта с журналом медленнее прежнего (11–24 с против
около 10 с) из-за поиска последнего номера журнала — заведено отдельной задачей.

**Что проверить, если сломается.** Во вкладке сети браузера у ответа
`/api/beads` должны быть `source: "cli-journal"` и `complete: true`, а запросы
идти раз в 5 с. Запросы раз в 15 с и `source: "cli"` — сервер ушёл на прежний
путь, смотреть его журнал (строки выше). Удалённая задача не пропадает с
доски — проверить, что `complete` доходит до `useBeads` (схема
`src/lib/api-schemas.ts`, `src/lib/beads-parser.ts`) и что условие слияния в
`use-beads.ts` его учитывает.
